1. Resumen

Sobre la base del Sprint 1 (registro, login y logout con 5 microservicios) se completaron los sprints 2, 3 y 4. Ahora la billetera permite ver el saldo y los movimientos, editar el perfil y el alias, asociar tarjetas, cargar dinero desde una tarjeta, ver y filtrar toda la actividad, y transferir a otras cuentas por CVU, CBU o alias, con un comprobante en PDF. También se cubrieron las épicas de testing: automatización con RestAssured, colección de Postman, testing exploratorio y QA sign-off. En infraestructura se sumaron las imágenes para AWS y la integración continua en GitHub Actions.

Sobre Docker. La PC donde se trabajó no puede ejecutar Docker. Para no dejar el entorno Docker sin probar, se armó un workflow de GitHub Actions que, en cada push, construye las imágenes, levanta el docker-compose completo (MySQL, MailHog y los 5 servicios) y corre contra él la automatización y la suite de casos. El resultado está en la sección 7.

2. Paso a paso: qué se hizo y con qué

#Qué se hizoHerramienta o framework, y para qué
1Subida a GitHub del Sprint 1 y lectura de las consignas de los sprints 2 a 4.Git: remoto origin y push de las tres ramas. Al cerrar cada sprint, dev se integra en test y main y se sube.
2Modelo de datos de los sprints 2 a 4, pensado de una vez: cuenta con saldo, tarjeta y movimiento.Spring Data JPA: entidades Card y Transaction, enums para tipos y marcas. BigDecimal para los montos, nunca double.
3Regla de acceso a una cuenta: solo el dueño o un administrador.Spring Security: el usuario del JWT se compara con el dueño de la cuenta (AccountAccess). Un usuario común recibe 403 aunque la cuenta no exista, para no revelar qué ids existen.
4Tarjetas: alta, listado, detalle y baja.Bean Validation para el formato; algoritmo de Luhn para el número; huella HMAC-SHA256 (javax.crypto) para detectar tarjetas repetidas sin guardar el número. El código de seguridad se valida y se descarta.
5Perfil: edición de nombre, apellido y teléfono; el registro devuelve el id de la cuenta.Spring MVC (@PatchMapping) y @PreAuthorize para "solo el propio usuario".
6Framework de automatización (módulo api-tests).RestAssured + JUnit 5: tests contra el sistema levantado entrando por el gateway, con etiquetas smoke y regression. Leen el código de verificación desde MailHog.
7Tiempos de caché de Eureka: el gateway tardaba hasta 90 s en ver un servicio recién levantado.Configuración de Eureka y de Spring Cloud LoadBalancer: ahora tarda unos segundos.
8Ingreso de dinero desde tarjeta.JPA con bloqueo pesimista (SELECT … FOR UPDATE) y optimista (@Version): dos ingresos simultáneos no se pisan el saldo.
9Actividad, detalle y filtros (monto, período, ingreso/egreso).JPA Specifications (Criteria API): la consulta se arma con los filtros presentes. Fechas en hora de Argentina.
10Testing exploratorio de los sprints 3 y 4: 79 pruebas en 4 sesiones, 5 defectos.Scripts de Python para peticiones simultáneas y repetidas.
11Corrección de defectos: tipos estrictos en el JSON, errores sin clases internas, filtro sin mayúsculas, idempotencia con huella, CVU con espacios.Jackson (configuración de coerción), un Converter de Spring y @RestControllerAdvice.
12Transferencias por CVU/CBU/alias.Transacción de Spring (@Transactional): débito y crédito juntos. Las dos cuentas se bloquean siempre en el mismo orden (id menor primero) para evitar deadlocks. OpenFeign trae el nombre del titular desde users-service; si no responde, la transferencia se hace igual.
13Idempotencia contra el doble envío.Header Idempotency-Key: la clave se guarda con una huella SHA-256 de la operación. El mismo pedido devuelve el original; la misma clave con otros datos devuelve 409.
14Comprobante en PDF.OpenPDF: genera el PDF con los mismos datos que el detalle de la actividad.
15Colección de Postman con 41 requests y scripts.Postman (formato v2.1). Se validó con un ejecutor equivalente, porque en la PC no hay Postman.
16Integración continua y prueba de Docker.GitHub Actions: compila y testea en cada push, construye las imágenes con el Dockerfile, levanta docker-compose y corre la automatización y la suite contra él.
17Imágenes para AWS y guía de despliegue.Workflow que publica en GitHub Container Registry y, si se configura, en Amazon ECR (con OIDC, sin claves guardadas). docker-compose.aws.yml para un servidor EC2. Guía para ECS Fargate + RDS.
18Documentación: planilla, exploratorios, QA sign-off, README y este informe.Python para la planilla .xlsx y Chrome sin interfaz para este PDF.

4. Decisiones técnicas

DecisiónPor qué
Montos con BigDecimal y escala 2Con double, 0,1 + 0,2 no da 0,3. Se verificó que 10 ingresos de $0,10 dan exactamente $1,00.
Bloqueo pesimista de las cuentas al mover dineroSin bloqueo, dos operaciones simultáneas leen el mismo saldo y una pisa a la otra. Probado con 12 ingresos y con 20 transferencias cruzadas al mismo tiempo.
Orden fijo de bloqueo (id menor primero)Si A→B bloquea A y espera B mientras B→A bloquea B y espera A, se trancan las dos (deadlock). Con orden fijo eso no puede pasar.
Idempotencia con huella de la operaciónUn doble clic o un reintento por timeout no repite la transferencia. Reusar la clave con otros datos es un error (409), no una respuesta silenciosa (defecto DEF-009).
Copia de los datos de la contraparte en el movimientoEl comprobante tiene que mostrar lo que fue, aunque después cambie el alias o se elimine la tarjeta.
Huella HMAC del número de tarjeta, no el númeroPermite detectar la misma tarjeta en otra cuenta (409) sin guardar el número. Un hash simple no alcanza: los números de tarjeta se pueden probar por fuerza bruta.
Datos del titular por Feign sin bloquear la operaciónEl nombre del titular no es necesario para mover el dinero: si users-service no responde, la transferencia se completa igual.
Tipos estrictos en el JSONEn una operación con dinero, "amount": "100" debe rechazarse, no adivinarse (defecto DEF-006).

7. Docker, integración continua y AWS

Resultado: CI en verde (ejecución #4, commit 08442ee). En un servidor de GitHub con Docker se construyeron las 5 imágenes, se levantó el entorno completo, pasaron los 75 casos RestAssured y la suite de la planilla contra MySQL y MailHog, y los datos siguieron ahí después de reiniciar los servicios. Las tres primeras ejecuciones fallaron por errores de los scripts de prueba del pipeline, no del sistema, y se corrigieron.

  • Integración continua (.github/workflows/ci.yml): en cada push, compila y corre los tests; después levanta docker-compose.yml, espera a que los servicios estén registrados en Eureka y corre la automatización RestAssured, la suite de casos y la prueba de persistencia en MySQL reiniciando los servicios.
  • Imágenes para AWS (.github/workflows/publish-images.yml): a pedido o con un tag v*, construye las 5 imágenes y las publica en GitHub Container Registry y, si se configura, en Amazon ECR.
  • Despliegue: docker-compose.aws.yml levanta el sistema en un servidor EC2 con las imágenes publicadas; docs/deploy-aws.md explica ese camino y el de ECS Fargate + RDS. No se desplegó en una cuenta real de AWS.
