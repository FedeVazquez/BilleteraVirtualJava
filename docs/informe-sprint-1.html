1. Resumen

Se construyó desde cero el backend del Sprint 1 como cinco microservicios con Java 21 y Spring Boot 3.5: registro de usuario con cuenta digital (CVU y alias), login con token JWT y logout que invalida el token. Se implementaron también las dos historias opcionales (verificación de email con código de 6 dígitos y recupero de contraseña por mail) y las tres épicas de soporte: testing, infraestructura y documentación.

72casos de prueba (70 pasan, 2 bloqueados)

Lo que no se pudo verificar. Docker Desktop no arranca en esta máquina: Windows no tiene habilitada la característica "Plataforma de máquina virtual", y habilitarla requiere permisos de administrador y reiniciar. Por eso el entorno con Docker Compose, MySQL y MailHog quedó escrito y validado en su sintaxis, pero no ejecutado. Todo lo demás se levantó y se probó de punta a punta con una base H2 en memoria y un servidor de correo falso. La sección 9 explica el problema y cómo destrabarlo.

5. Cómo funciona cada historia

Registro — POST /users/register

  1. El gateway recibe la petición. La ruta es pública, así que no pide token, y la envía a users-service (lo ubica en Eureka).
  2. Bean Validation revisa el body. Si algo está mal responde 400 con el detalle por campo.
  3. UserService verifica que el email y el DNI no existan (400 si existen), calcula el hash BCrypt de la contraseña, asigna el rol ROLE_USER, genera el código de verificación y guarda el usuario con JPA.
  4. Con Feign llama a account-service, que genera un CVU de 22 dígitos y un alias de 3 palabras del archivo alias-words.txt, comprueba que no estén repetidos y guarda la cuenta.
  5. Todo el paso 3 y 4 ocurre dentro de una transacción (@Transactional): si account-service falla, el usuario no queda guardado y se responde 500.
  6. Después del commit, Spring Mail envía el código de 6 dígitos.
  7. Respuesta 201 con los datos del usuario, el CVU y el alias. El DTO de respuesta no tiene campo de contraseña.

Login — POST /auth/login

  1. El gateway envía la petición a auth-service (ruta pública).
  2. AuthService pide las credenciales a users-service por Feign. Si el usuario no existe, el ErrorDecoder convierte el 404 en la misma respuesta 404 para el cliente.
  3. BCrypt compara la contraseña con el hash: si no coincide, 400. Si el email no fue verificado, 403.
  4. jjwt emite el token, válido por 60 minutos. Como el token no depende de una sesión guardada en el servidor, recargar la página no cierra la sesión: alcanza con que el frontend lo conserve y lo envíe en cada petición.

Logout — POST /user/logout

  1. El token viaja en el header Authorization: Bearer …. El gateway lo valida y pasa la petición a auth-service.
  2. auth-service guarda el identificador del token (jti) en la tabla de tokens invalidados y responde 200.
  3. Desde ese momento, el filtro del gateway rechaza ese token con 401, porque en cada petición le pregunta a auth-service si el token sigue siendo válido. Un JWT no se puede "borrar"; por eso hace falta esa lista.

Opcionales

  • Verificación de email: sin verificar, el login responde 403. POST /auth/verify-email con el código lo habilita. El código vence a los 15 minutos y se bloquea tras 5 intentos fallidos; se puede pedir otro.
  • Recupero de contraseña: POST /auth/forgot-password envía un mail con un link a reset-password.html, una pantalla que pide la contraseña nueva dos veces. El link vence a los 30 minutos y sirve una sola vez. En la base se guarda solo el hash del token. Cambiar la contraseña cierra todas las sesiones abiertas del usuario.

6. Decisiones de seguridad

  • Contraseñas: solo se guarda el hash BCrypt. Ninguna respuesta las incluye.
  • Roles: entidad Rol asociada al usuario (ROLE_USER, ROLE_ADMIN). Los datos de un usuario y su cuenta solo los puede ver su dueño o un administrador (403 para el resto). No se incluyó un alta de administradores: hoy todo usuario registrado es ROLE_USER.
  • Endpoints internos (/internal/**): no tienen ruta en el gateway y exigen una clave compartida entre servicios.
  • Defensa en dos capas: el gateway valida el token contra auth-service y, además, cada servicio vuelve a verificar la firma y los permisos.
  • Secretos: se leen de variables de entorno. Los valores por defecto del código son solo para desarrollo local y hay que cambiarlos en cualquier otro entorno.
  • Códigos de respuesta del login: se respetó la consigna (404 y 400). Eso permite distinguir si un email está registrado; está anotado como observación para conversar con el negocio.

8. Infraestructura propuesta

En el entorno local todo corre en una red interna de Docker con un único puerto publicado para la API (sección 3). Para producción se propone separar tres subredes: una pública con el balanceador (HTTPS), una privada con los servicios duplicados en dos zonas, y una de datos con MySQL primario y réplica, más almacenamiento de objetos para backups y logs. El detalle y la justificación de cada componente están en docs/infraestructura.md.

Docker Desktop no arrancaPrimero falló por archivos de socket residuales de una ejecución anterior; se renombraron las carpetas que los contenían (AppData\Local\Docker\run y docker-secrets-engine) para que Docker las recree. Superado eso, el log mostró la causa de fondo: "Virtual Machine Platform not enabled". Se resolvió con el argumento de JVM -Djdk.net.unixdomain.tmpdir=Q:\no-existe, que hace que Java use TCP.Si al ejecutar desde Eclipse aparece ese error, agregar ese argumento en VM arguments. Si no aparece, no hace falta.

10. Cómo abrirlo y ejecutarlo

En Eclipse

  1. File → Import → Maven → Existing Maven Projects. Elegir la carpeta DigitalMoneyHouse y dejar marcados los 6 proyectos.
  2. Verificar en Window → Preferences → Java → Installed JREs que el JRE sea 17 o superior (el instalado es el 21).
  3. Para cada servicio, botón derecho sobre su clase *Application → Run As → Java Application. Primero EurekaServerApplication; al final ApiGatewayApplication.
  4. Sin Docker: en Run Configurations → Arguments → VM arguments de auth-service, users-service y account-service, agregar -Dspring.profiles.active=h2.
  5. Para correr los tests: botón derecho sobre un proyecto → Run As → JUnit Test.

Desde la terminal

.\mvnw.cmd verify                      # compila y corre los 125 tests
.\scripts\start-local.ps1              # levanta todo sin Docker (perfil h2)
python scripts\run_test_suite.py       # ejecuta los 72 casos de prueba
.\scripts\stop-local.ps1               # apaga todo

docker compose up -d --build           # todo con Docker, cuando esté disponible

Con el sistema levantado: API en http://localhost:8090, Swagger UI en http://localhost:8090/swagger-ui.html y panel de Eureka en http://localhost:8761.
